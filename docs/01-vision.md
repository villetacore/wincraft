# Видение и стратегия

## 1. Продуктовая цель

WinCraft должен стать самостоятельной открытой настольной ОС: пользователь скачивает ISO, загружает компьютер, проверяет оборудование, устанавливает систему, запускает привычные программы и получает обновления без потери данных. Знакомый интерфейс Windows нужен для удобства, но основная ценность — рабочие приложения, восстановление и предсказуемость.

Проект не является форком Windows: в репозитории нет её исходной базы. «Открытая альтернатива Windows с Unix-архитектурой» — корректное описание направления. Если появится форк конкретного upstream-компонента, его происхождение и патчи фиксируются отдельно.

ReactOS — ориентир по идее независимой совместимости, но использует NT-подобную архитектуру. WinCraft на существующей базе выбирает иной способ достижения пользовательского результата: Unix/Linux, слой совместимости и собственное окружение. См. [описание архитектуры ReactOS](https://reactos.org/architecture/).

Направление согласовано 14.10.2026: Linux остаётся фундаментом, собственное окружение развивается на Rust, Wine становится управляемой платформой приложений. Исследование ядра ведётся отдельно. Ближайшее преимущество WinCraft — предсказуемые установка, запуск, диагностика и восстановление приложений, а также сохранность документов. Сначала подтверждаются 5–10 выбранных реальных программ; большой каталог остаётся долгосрочной целью.

## 2. Приоритет требований

| Приоритет | Требование | Проверяемый результат |
| --- | --- | --- |
| P0 | Самостоятельная загрузка | ISO загружается в чистой VM без установленной ОС |
| P0 | Целостность данных | Перезагрузка, обновление и восстановление не теряют пользовательские файлы |
| P0 | Базовая безопасность | Desktop и EXE не работают от root; привилегированные операции ограничены |
| P1 | Windows-приложения | Проходят опубликованный набор реальных сценариев |
| P1 | Rust | Новый собственный системный код пишется на Rust, исключения документируются |
| P1 | Установка и обновления | Есть установка на выделенный диск и возврат к предыдущему выпуску |
| P1 | Unix-окружение | Терминал, сеть, процессы, файловые права и нативные приложения |
| P2 | DOS и старое ПО | Отдельные профили эмуляции и тестовые сценарии |
| P2 | Реальные компьютеры | Поддерживается ограниченная опубликованная матрица устройств |
| R&D | Собственное Rust-ядро | Отдельные измеримые этапы; не условие выпуска Linux-редакции |

«Почти весь современный софт» преобразуется в цель покрытия выбранного каталога. Нельзя вычислить процент от неопределённого множества. Для 1.0 предлагается каталог из 100 фиксированных версий приложений и цель не менее 90 полностью прошедших обязательные сценарии; это целевой показатель, не прогноз и не сегодняшняя совместимость. Неудачные программы не исключаются из знаменателя ради красивой цифры.

## 3. Три возможные стратегии

| Стратегия | Выигрыш | Стоимость и ограничение | Рекомендация |
| --- | --- | --- | --- |
| Linux + Rust services + Wine | Быстрый путь к драйверам, ISO и существующим приложениям | Значительная часть платформы на C/C++; зависимость от upstream | Основная продуктовая ветка |
| Собственное Unix-ядро на Rust + порт Wine | Контроль архитектуры и собственного ядра | Нужно заново создать процессы, память, ABI, драйверы, графику; POSIX недостаточно | Исследовательская ветка |
| NT-совместимое ядро на Rust | Более прямой путь к NT kernel ABI | Огромный объём семантики NT и моделей драйверов; конфликт с простотой Unix-ядра | Только отдельное решение после доказательства необходимости |

Виртуализация Windows — дополнительный режим, а не четвёртая собственная реализация Windows API. Она требует отдельной гостевой системы и прав на её использование; нельзя включать её результаты в показатель нативной совместимости WinCraft.

## 4. Что значит «на Rust»

В основной ветке Rust используется для init/supervisor, оболочки, файлового менеджера, менеджера приложений, runtime broker, установки, обновлений, диагностики и публичного SDK. Существующие Linux, Wine, Mesa и другие компоненты не становятся Rust-кодом от использования Rust-оболочки. Поддержка Rust внутри Linux также не означает переписывания Linux на Rust: [документация ядра](https://www.kernel.org/doc/html/latest/rust/index.html).

Собственное ядро — самостоятельная цель из отдельного документа. Если принципиально требуется весь собственный kernel-код на Rust, допустим минимальный assembler для загрузки и архитектурных переходов; сторонние библиотеки, прошивки и ABI остаются предметом явной политики. «100% Rust» не должно маскировать зависимость от C-компонентов.

Не переписывать зрелые компоненты ради языка. Переписывание оправдывается измеримой проблемой безопасности, сопровождаемости или функциональности и сравнением с upstream-решением.

## 5. Пользовательские сценарии

1. **Знакомство:** live ISO, выбор языка и раскладки, открытие файлов, запуск демонстрационного Windows-приложения, завершение работы.
2. **Повседневная работа:** браузер, редактор, документы, архивы, USB-накопитель, звук, печать, сеть и несколько мониторов на поддержанном оборудовании.
3. **Windows-программа:** пользователь выбирает EXE/MSI, видит проверенный профиль или статус «не проверено», устанавливает, открывает документ, сохраняет и удаляет приложение.
4. **Игра:** выбирается runtime и графический backend; пользователь видит требования GPU и известные ограничения конкретной игры.
5. **DOS:** отдельное окружение с диском, ограниченным каталогом обмена, клавиатурой и звуком.
6. **Разработка:** терминал, Git, Rust toolchain, нативные Linux-инструменты; Windows toolchain проверяется отдельно.
7. **Восстановление:** неудачное обновление не блокирует доступ к предыдущему выпуску и данным.

## 6. Границы первых выпусков

Начальная архитектура CPU — x86-64, Windows x64 и x86 в проверенной конфигурации Wine. ARM64, трансляция x86 на ARM и загрузка 32-битной ОС откладываются. Первая аппаратная платформа — QEMU q35; затем небольшая матрица конкретных ПК. UEFI без Secure Boot — первая цель ISO. BIOS — дополнительный тестируемый режим, Secure Boot — отдельный этап с ключами и политикой доверия.

В 1.0 не обещаются произвольные Windows kernel-драйверы, все античиты, вся экосистема Microsoft Store, стопроцентная совместимость Microsoft 365/Adobe/CAD, доменное управление уровня Windows Server, Xbox и телефонные платформы. Эти направления остаются в матрице исследований. Их отсутствие не скрывается за формулировкой «поддерживает EXE».

## 7. Долгосрочный принцип

Сначала полезная устанавливаемая система и измеряемая совместимость, затем расширение аппаратуры и API. Новая архитектура принимается, когда улучшает реальные сценарии и выдерживает обслуживание, а не только загружается в демонстрационной VM.
