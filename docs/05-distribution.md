# Сборка, ISO, установка и обновления

Все новые артефакты и команды в этом документе — спецификация будущей реализации. Сейчас скрипты создают `vmlinuz` и `initramfs.cpio.gz`, а не ISO.

## 1. Форматы поставки

| Артефакт | Назначение |
| --- | --- |
| Live ISO x86-64 | Проверка системы без изменения дисков, запуск установщика |
| Установленная система | Постоянные данные, bootloader, обновления и recovery |
| Developer kernel/initrd | Быстрая текущая QEMU-загрузка и отладка |
| VM image, позже | Удобство тестирования; производный артефакт той же сборки |
| Update bundle | Подписанная системная версия и manifest |
| Source bundle + SBOM | Происхождение кода, зависимости, лицензии и воспроизводимость |

Существующий data.ext4 — диск данных разработчика, не установленная ОС. Его автоматическое подключение в текущем launcher нельзя переносить на произвольные физические диски.

## 2. Загрузочная цепочка live ISO

```text
UEFI firmware
  -> EFI bootloader на носителе
  -> Linux kernel + небольшой early initramfs
  -> найти носитель по метке/UUID, проверить manifest
  -> смонтировать read-only rootfs.squashfs
  -> создать writable слой в RAM
  -> overlay root + switch_root
  -> system supervisor -> user session -> desktop
```

OverlayFS объединяет нижний и верхний слои, но для writable upper существуют требования к файловой системе и xattrs; их нужно учитывать при persistent mode. См. [документацию OverlayFS](https://docs.kernel.org/filesystems/overlayfs.html).

Первый вариант: GRUB как кандидат bootloader и xorriso как инструмент упаковки; конкретные версии, EFI/BIOS modules и лицензии фиксируются сборкой. Не писать собственный загрузчик только для получения ISO.

Проектный layout носителя:

```text
/EFI/BOOT/BOOTX64.EFI
/boot/grub/grub.cfg
/boot/vmlinuz
/boot/initramfs.img
/wincraft/rootfs.squashfs
/wincraft/manifest.json
/wincraft/manifest.sig
/licenses/
```

Фактическая hybrid ISO-разметка должна содержать необходимые загрузочные структуры для optical и USB-режима; наличие каталога EFI само по себе не делает образ загрузочным. Меню: normal, safe graphics, recovery, memory/diagnostic options при наличии.

Первый gate — UEFI VM без Secure Boot. BIOS и USB disk boot проверяются отдельными заданиями перед заявлением их поддержки. Secure Boot планируется отдельно: управление ключами, доверенная цепочка загрузки, подписи loader/kernel и политика module loading. Подпись ISO-пакета не равна Secure Boot.

## 3. Build pipeline

1. Проверить build manifest: source revision, toolchain, target, kernel config, пакеты и hashes.
2. Подготовить чистый builder, отделённый от пользовательской системы и секретов.
3. Получить зависимости с проверкой подписи/хеша, сохранить исходники и сведения о лицензиях.
4. Собрать Rust с `--locked`; выполнить релевантные unit/integration tests.
5. Создать rootfs в staging-каталоге; добавить только runtime-зависимости.
6. Создать обычного live-пользователя и production policy, исключить build cache и debug backdoors.
7. Собрать initramfs, squashfs, bootloader и ISO.
8. Запустить именно этот ISO в VM; проверить запуск и сценарии приложений.
9. Сформировать checksums, manifest, SBOM, source bundle и release notes.
10. Подписать артефакты только в release job после прохождения gates.

Builder root-права не должны означать доступ к реальным дискам хоста. Privileged операции изолировать; rootless steps использовать там, где возможно. Network fetch отделить от deterministic build; сетевые ошибки не должны приводить к использованию непроверенного кэша.

Для повторяемости закреплять не только Cargo.lock: snapshot пакетного репозитория, toolchain, compiler/linker, boot tools, build flags, fonts/assets и версии firmware. Упорядочить файлы, timestamps, owner IDs и compressor settings. Задать `SOURCE_DATE_EPOCH`. Верифицировать две чистые сборки; если hashes различаются, сначала локализовать отличия, а не объявлять воспроизводимость по одному manifest.

## 4. Установщик

Первый поддержанный режим — **чистая установка на явно выбранный выделенный диск**. Dual boot, уменьшение чужих разделов и автоматическая миграция Windows откладываются до отдельного плана сохранности данных.

UI: язык/раскладка → проверка оборудования → список дисков с model/size/serial → план разделов → учётная запись → итоговый экран → явное подтверждение стирания выбранного диска → выполнение → проверка → reboot.

Предлагаемая GPT-разметка для A/B:

| Раздел | Формат | Роль |
| --- | --- | --- |
| ESP | FAT32 | Загрузчик, записи boot, recovery entry |
| SYSTEM_A | ext4 или образ на FS | Активная системная версия |
| SYSTEM_B | Такой же | Следующая/предыдущая версия |
| DATA | ext4 | `/home`, runtime state, изменяемая конфигурация |

Размеры вычисляются по manifest: обе системные версии должны помещаться с запасом, DATA получает оставшееся пространство. Не публиковать минимальные размеры до измерения реального образа. Для начального тестового стенда планировать 4 GiB RAM и 32 GiB disk как бюджет, не гарантированный минимум.

Storage backend повторно проверяет идентичность диска перед записью, исключает загрузочный носитель и занятые volumes, блокирует параллельные операции и пишет журнал фаз. Пути `/dev/sda` недостаточно для устойчивой идентификации. При unplug или изменении таблицы разделов план становится недействительным.

Запись начинается только после просмотра конкретного плана. Создание пользователя и пароля не пишет секреты в журнал. По завершении проверяются filesystem, manifest, boot entries и возможность следующей загрузки. При ошибке пользователь получает точную фазу и recovery-инструкцию; нельзя показывать «установлено» до проверки.

## 5. Обновления

Рекомендация — образные атомарные обновления A/B. Package manager используется для сборки поставки; произвольное изменение системных пакетов пользователем не является основным release path.

Алгоритм: загрузить во временное место → проверить доверенную подпись и совместимость manifest → проверить свободное место → записать неактивный slot → проверить содержимое → выставить trial boot → загрузить → выполнить health check → подтвердить slot. При незавершённом trial после ограниченного числа попыток выбрать предыдущий slot.

Health check включает доступность persistent data, essential services и работоспособность сессии; простого запуска kernel недостаточно. Сбой питания на каждой фазе — обязательный тест. Отказ новой версии не должен уничтожать последнюю рабочую.

Подпись хранится отдельно от TLS: HTTPS защищает транспорт, а подпись — доверие к release. Нужны ротация ключей, отзыв скомпрометированных ключей и защита от несанкционированного downgrade. Разрешённый recovery rollback имеет отдельную политику.

Состояние `/etc`, системных БД и app prefixes не автоматически откатывается вместе с root. Миграции должны поддерживать предыдущую версию либо создавать snapshot/backup до изменения. Перед обновлением prefix — копия и проверка совместимости; runtime можно удержать старым для конкретного приложения. Документы пользователя не откатываются вместе с ОС.

## 6. Recovery и носители

Recovery позволяет загрузить предыдущую систему, просмотреть логи, экспортировать данные и проверить FS. Не должен молча форматировать диск или открывать unauthenticated root shell в release. Debug ISO маркируется отдельно.

Full-disk encryption планируется после базового installer: key management, unlock UI, recovery key и сценарий утери ключа. Нельзя добавлять шифрование без восстановления и проверок power loss. Secure Boot и disk encryption решают разные задачи.

## 7. Acceptance ISO/install/update

- ISO загружается без `-kernel/-initrd` в чистой UEFI VM.
- Live mode не изменяет внутренние диски автоматически.
- После установки ISO извлекается, VM загружается с диска, документы сохраняются.
- Ошибочный/подменённый update отклоняется до активации.
- Отключение питания в каждой фазе update сохраняет путь к старой версии.
- Нет root desktop, `X -ac` и открытого serial shell в release.
- Неподдержанная firmware/hardware configuration показывается как ограничение, не как пройденный тест.
