# Дорожная карта

Версии ниже — рабочие обозначения этапов, не объявленные даты выпуска. Каждый этап заканчивается проверяемым артефактом. Сроки — ориентиры планирования при наличии опытного разработчика, а не гарантия; зависимости и результаты экспериментов важнее календаря.

## 1. Порядок зависимостей

```text
M0 baseline -> M1 reliability/ISO -> M2 app/runtime -> M2.5 daily VM
                                                           |
                                                           v
M6 1.0 <- M5 beta <- M4 desktop/hardware <- M3 installer/update

R0..R6 own Rust kernel: отдельная ветка, не зависимость M1..M6
```

Работы внутри этапов могут чередоваться, но milestone не закрывается без gates. Нельзя компенсировать отсутствие rollback большим количеством работающих игр.

## 2. Этапы

### M0 — baseline и спецификация, ориентир 1–3 недели

Закрепить исходники, build inputs и статусы. Использовать существующий Git-репозиторий, выбрать собственную лицензию, создать issue tracker и manifest. Повторить текущую сборку в чистом окружении; сохранить log и hashes. Зафиксировать 5–10 реальных приложений; технические fixtures учитывать отдельно. Проверить риск musl/glibc и x86 runtime.

**Gate:** сборка текущего rootfs из чистого builder, QEMU smoke в сохранённой конфигурации, отчёт о реальной x64/x86 поддержке, лицензии/источники известных компонентов, принятое решение по base/runtime.

**Артефакт:** baseline image и воспроизводимая инструкция. Не менять одновременно все UI и bootstrap.

### M1 / 0.3 — завершение надёжности существующего live ISO

Early initramfs, squashfs, overlay, bootloader, обычный пользователь и X authorization уже есть в коде. Завершить приёмку, исправить FIX-01…04: readiness Wine, ошибки bind-mount, ошибки spawn сессии, безопасное сохранение документов. Проверить recovery, crash limit и debug/release границу. Повторно создавать работающие компоненты не нужно.

**Gate:** 10 последовательных успешных загрузок ISO в целевой UEFI VM, desktop под обычным UID, EXE demo, safe shutdown, неприкосновенность чужих дисков, отсутствие release root shell. Отдельно: отказ wineboot не выдаёт ready; ожидание ограничено; отказ bind-mount явно виден; ошибка spawn приводит к ограниченному retry/recovery; ошибка сохранения не уничтожает прежний файл; документ сохраняется после reboot с диском данных.

**Артефакт:** developer live ISO. Этот выпуск ещё не установщик и не система общего назначения.

### M2 / 0.4 — управляемая совместимость, 4–10 недель

Форматный detector, structured launch, versioned runtimes, per-app prefixes, готовность Wine, install/uninstall, logging, permissions. Проверить x86 и x64 отдельно; добавить MSI. DOS backend — дополнительная задача P2, не gate этого preview. Каталог 5–10 реальных приложений плюс отдельные fixtures и воспроизводимые сценарии. Измерить, а не предполагать, пригодность glibc/runtime решения.

**Gate:** чистое окружение для каждого приложения, результаты install/open/save/reopen/uninstall, отсутствие смешивания prefixes, понятная ошибка для неподдержанного формата; все записи выбранного каталога имеют результат, а blocking fixtures проходят.

**Артефакт:** compatibility preview с матрицей ограничений. Успех baseline fixtures не заменяет real-app testing.

### M2.5 — повседневные сценарии в VM

Интегрировать готовые службы сети и звука, нативный браузер, базовый ввод RU/EN. GUI обращается к их API; собственные сетевой стек и аудиосервер не нужны. Тестировать в явно заданной VM-конфигурации с сетью и виртуальным аудиоустройством; существующая конфигурация -nic none этого не проверяет.

**Gate:** браузер открывает HTTPS-страницу и сохраняет файл; после reboot файл доступен на диске данных; звук воспроизводится; потеря сети и восстановление соединения дают понятное поведение. Сохраняются версии и журналы. Прохождение VM-сценариев не означает поддержку Wi-Fi или звука реальных ПК.

**Артефакт:** ограниченный повседневный preview. Этап предшествует установщику; расширенная периферия остаётся M4.

### M3 / 0.5 — установка и жизненный цикл, 6–12 недель

Установка на выделенный диск, пользователь/пароль, persistent home, A/B slots, подписанный update, trial boot, recovery, schema migrations. Тесты поломок диска и питания выполняются на disposable VM disks.

**Gate:** install → remove ISO → boot → create document → update → boot → rollback → reopen document. Подмена подписи и нехватка места корректно отклоняются. Power-loss tests не оставляют систему без рабочей загрузки.

**Артефакт:** устанавливаемый alpha ISO и update bundle. Dual boot ещё не заявляется.

### M4 / 0.6–0.8 — desktop и оборудование, несколько кварталов

Network/audio/printing, USB, RU/EN/IME, DPI, accessibility, session locking, power management. Проверенная аппаратная графика, игровая ветка, каталог 30–50 приложений. Выбрать 2–3 реальные аппаратные конфигурации и вести HCL. Wayland проходит отдельный сравнительный gate, до этого сохраняется рабочий X11 path.

**Gate:** опубликованы аппаратные отчёты, desktop scenarios и регрессии; suspend/resume, Wi-Fi reconnect, external display и sound работают на заявленных устройствах. Производительность измерена на одинаковой конфигурации.

**Артефакт:** hardware preview. Не обобщать успех трёх устройств на все ПК.

### M5 / 0.9 — beta, ориентир 1–2 квартала стабилизации

Заморозить supported catalog, release policy, security triage и migration path. Добавить soak tests, локализацию, документацию пользователя и диагностический export. Подготовить поддержку пользователей и владельцев компонентов.

**Gate:** нет открытых release-blocking проблем потери данных, boot/install/update и privilege boundary; поддержанные приложения проходят обязательные сценарии, все ограничения опубликованы. Два последовательных beta update проходят миграцию и rollback.

### M6 / 1.0 — ограниченно поддерживаемый стабильный продукт

Предлагаемые цели: 100 фиксированных приложений в каталоге, ≥90 полностью проходящих сценарии; 100% критических сценариев ОС; подтверждённые HCL и update path. Значения требуют ресурсов и корректируются только публичным решением до релиза. Если критерии не выполнены — продолжить beta или сузить объявленную продуктовую область, не переименовывать partial в pass.

1.0 означает стабильность опубликованного контракта, а не завершённую реализацию Windows. Обязательны владельцы security/update infrastructure, сроки поддержки и процедура end-of-life.

## 3. Первые 90 дней одного разработчика

Это порядок работы при неполной определённости, а не обещание закончить все milestones за три месяца.

| Период | Основной результат | Что измерить |
| --- | --- | --- |
| Недели 1–2 | M0: clean baseline, каталог, manifest | Собирается ли система, x86/x64, inputs |
| Недели 3–4 | FIX-01…04 | Ошибки Wine, mounts, spawn и сохранения |
| Недели 5–6 | Приёмка имеющегося ISO и recovery | 10 cold boots, UID, X auth, reboot с данными |
| Недели 7–8 | M1 gate и runtime broker skeleton | Повторные boot, ready prefix, logs |
| Недели 9–10 | Per-app profiles и x86/MSI tests | Install/save/reopen/uninstall |
| Недели 11–12 | Реальные app results и M2.5 spike | Браузер, сеть, звук в VM; следующий план |
| Оставшийся резерв | Исправления и документация | Закрыты ли gates, а не количество features |

Если M1 задерживается, не начинать installer и собственное ядро одновременно. После каждого двухнедельного цикла пересматривать оценку по фактической скорости и числу дефектов.

## 4. Ресурсы

Один разработчик способен развивать прототип и ограниченный дистрибутив, но широкая современная Windows-совместимость, аппаратная поддержка и безопасные релизы — многолетняя работа с опорой на upstream. Для небольшой команды разделить ownership: platform/build, Rust desktop, compatibility, QA/release. Один человек может совмещать роли, но задачи никуда не исчезают.

Нужны CI storage, проверенные installers, signing infrastructure, Windows test environment для сравнительных тестов при допустимых условиях, несколько GPU/ПК, backup и security response. Размер бюджета определяется выбранной HCL и кадровым планом; точная денежная оценка без этих данных была бы выдумкой.

Предлагаемое распределение раннего ресурса: 60% platform/reliability, 25% compatibility, 15% UI/documentation. Rust-kernel R&D — только из отдельно выделенного времени, чтобы не съедать релизный минимум.

## 5. Критерии остановки и пересмотра

- База не запускает обязательный runtime без значительного patch set: пересмотреть libc/base до M2.
- Обновление вызывает потерю данных: остановить новые функции до исправления и recovery test.
- Собственный supervisor требует несоразмерного сопровождения: интегрировать существующий.
- Собственное ядро не имеет отдельного владельца: оставить спецификацию, не блокировать desktop.
- Vendor-only сценарий зависит от недоступной аттестации: отметить unsupported/blocked, не тратить бесконечный срок на ложное обещание.
