# Архитектурные решения и риски

Согласование направления владельцем 14.10.2026 фиксирует Linux, Rust-компоненты, управляемый Wine и отдельное исследование ядра. Принятое решение не означает готовую реализацию. Статусы: «рекомендовано» означает решение этого плана, ещё не реализацию и не отдельное подтверждение владельцем проекта; «открыто» требует данных. Изменения решений фиксируются новым ADR с причинами и миграцией.

## 2. ADR-018: Wayland вместо Xorg

**Контекст.** Владелец проекта потребовал Wayland вместо Xorg (14.10.2026), раньше этапа M3, на котором его планировал ADR-011. В 0.4 Xorg работал от root, а X11 не изолирует ввод и окна программ одного пользователя друг от друга. Openbox был временным оконным менеджером первого этапа.

**Решение.**

- Композитор и оконный менеджер — **labwc 0.9** (wlroots 0.19) из upstream-исходников, собственный пакет `distro/package/labwc`. Это прямой Wayland-аналог Openbox: тот же формат `rc.xml` и тем, кнопки заголовка как в Windows. Собственный композитор на Rust (бывший пункт «wc-wm») остаётся следующим этапом, а не предпосылкой.
- **seatd** (root) — единственная привилегированная часть графики. Композитор работает от UID 1000, с программным рендерингом (`WLR_RENDERER=pixman`) до появления GPU-01; клиенты рисуют через Mesa/llvmpipe (EGL).
- Оболочка — обычный Wayland-клиент (`crates/wc-wayland`). Рабочий стол и панель задач — поверхности wlr-layer-shell (фон и верхний слой; панель резервирует 48 px). Список окон панели задач берётся из wlr-foreign-toplevel-management. «Пуск», «Выполнить» и сообщения — обычные окна, их размещают правила `windowRules` labwc. Остальные окна (Проводник, Блокнот, Диспетчер задач) — xdg-toplevel через winit, с серверными рамками labwc.
- **Windows-программы — через XWayland** (драйвер Wine `winex11`): это самый совместимый путь, так же работает Proton. Родной драйвер `winewayland.drv` требует `libxkbregistry`, а пакет libxkbcommon Buildroot его отключает. Включение — отдельный шаг с выбором драйвера в профиле приложения (APP-01/03), без смены поведения по умолчанию.
- Терминал — foot (Wayland) вместо xterm. Сеанс: `winlogon` → seatd → labwc (`--startup "winlogon --report-session"` сообщает `WAYLAND_DISPLAY`/`DISPLAY`) → Wine prefix → explorer.

**Отклонено.** Собственный композитор на Smithay сейчас: смена дисплейного сервера, оконного менеджера, рамок и XWayland-WM одновременно, без возможности проверить по частям. sway/cage: нет плавающих окон с кнопками заголовка как в Windows. Weston: нет протоколов для панели задач.

**Последствия и цена.** XWayland-клиенты по-прежнему видят друг друга (один X-сервер на сеанс); нативные Wayland-клиенты изолированы. Сокет Xwayland не защищён cookie: в образе один пользователь, служб с другими UID, подключающихся к дисплею, нет. Это ограничение записано для APP-07. Смена базы требует пересборки Mesa (платформа wayland, GBM). Переходный Alpine-конвейер 0.3 переведён на те же компоненты.

**Что потребовалось при проверке.** wlroots сам повторно открывает DRM-устройство для буферов, поэтому `/dev/dri/card*` принадлежит группе `video` (правило `70-wincraft-graphics.rules`), а пользователь сеанса в неё входит. Параметр ядра `fbcon=nodefer`: при отложенном захвате консоли (ядра Alpine) к старту labwc режим экрана не установлен, и первый modeset не завершается. Оболочка пересоздаёт закрытые композитором layer-поверхности, как explorer.exe пересоздаёт панель задач. В отладочной загрузке журнал композитора пишется в `/run/user/1000/labwc.log`.

## 3. Подробно о главном выборе

**Контекст:** пользователь хочет Unix-основу, Rust, ISO и почти весь современный Windows software. Текущий репозиторий уже является Linux-based prototype. Собственное ядро означает повторную реализацию инфраструктуры, которой сейчас пользуются Wine и desktop.

**Решение:** основная ветка достигает пользовательского результата через Linux и зрелые runtime; собственные службы развиваются на Rust. Новое Rust-ядро имеет отдельные gates.

**Отклонённая для первого продукта альтернатива:** удалить текущую базу и сначала написать универсальное Unix/NT kernel. Это не устраняет задачу Wine, GUI, драйверов и библиотек, а добавляет её фундамент.

**Цена решения:** зависимость от C/C++ upstream, необходимость соблюдать их лицензии, невозможность честно назвать всё ядро собственным Rust-кодом. Если это неприемлемо для владельца, приоритет меняется на R&D и ограниченную первоначальную совместимость. Архитектура не скрывает этот выбор.

## 4. Реестр рисков

Оценки качественные, не статистические вероятности.

| Риск | Вероятность / ущерб | Ранний сигнал | Мера и условие пересмотра |
| --- | --- | --- | --- |
| Разрастание «вся Microsoft тема» | Высокая / критический | Нет конечного каталога | Заморозить scope и сценарии до M2 |
| Несовместимость base/runtime | Средняя / высокий | Сборка требует растущих hacks | Сравнить glibc до закрепления образа |
| Регрессия прав сессии | Возможна / критический | UID=0 в desktop/EXE | SEC-01 реализован; повторять проверку UID и X auth перед preview |
| Потеря данных installer/update | Средняя / критический | Нет fault tests | Только disposable VM tests до hardware install |
| Ложная оценка совместимости | Высокая / высокий | Есть только screenshot startup | Обязательные end-to-end scenarios |
| Драйверы/anti-cheat/vendor policy | Высокая / высокий | Требуется proprietary kernel/attestation | Отдельный unsupported status и bounded research |
| Supply chain | Средняя / критический | Плавающие зависимости, нет signatures | Pinned inputs, audit, signed releases |
| Недостаток сопровождающих | Высокая / высокий | Нет владельца security/update | Сузить поддержанный scope и сроки |
| Kernel R&D поглощает desktop | Высокая / высокий | Месяцы без boot/install улучшений | Отдельный ресурс и release gates |
| Hardware regressions | Высокая / высокий | Проверяется только QEMU | Ограниченная HCL и повторная сертификация |
| Невоспроизводимые сборки | Высокая сейчас / средний | Разные APK versions/chroot state | Чистый builder и diff артефактов |
| Лицензии/assets неизвестны | Средняя / высокий | Нет provenance | Inventory до распространения |

## 5. Открытые вопросы и значения по умолчанию

| Вопрос | Рабочее предположение | Когда пересмотреть |
| --- | --- | --- |
| Главное — приложения или новое ядро? | Согласован desktop плюс отдельное ядро R&D | Только при явном изменении цели владельцем |
| Какие приложения обязательны? | Каталог фиксируется M0, без заранее объявленного pass | До M2 |
| Размер команды и бюджет? | Один разработчик; milestones без обещанных дат | После первых двух итераций |
| Целевые ПК? | QEMU q35, затем 2–3 выбранные конфигурации | До M4 |
| Closed-source компоненты? | Открытая base; optional downloads только на допустимых условиях | До inclusion/runtime design |
| Dual boot? | Не входит в первый installer | После надёжного standalone install |
| Secure Boot? | Отдельный этап после UEFI ISO | После threat model и key ownership |
| NT driver compatibility? | Не входит в Linux product contract | При конкретном аппаратном требовании |

## 6. Как принимать новые решения

ADR должен содержать проблему, альтернативы, эксперимент, результаты, выбранный путь, стоимость сопровождения и migration/rollback. Слова «современный», «быстрый», «полностью совместимый» заменяются измеряемыми требованиями. Спор о языке реализации не заменяет тесты поведения API и сохранности данных.

## 7. Уточнения после анализа 0.3

- ReactOS — источник изучения NT и совместимости, не новая база WinCraft. Перенос Windows/ReactOS-драйверов на Linux не входит в продуктовую ветку.
- Главный пользовательский результат: установка → профиль приложения → ярлык → открытие/сохранение документа → диагностика → удаление либо восстановление окружения.
- Alpine сохраняется до сравнения с одной glibc-базой: одинаковые версии приложений, x86/x64, браузер, звук, графика, размер образа и стоимость сопровождения. Смена базы требует отчёта, не только предпочтения libc.
- Read-only образ — уже имеющаяся основа будущего восстановления. A/B и подписанные обновления ещё проектируются. Откат системы не равен откату документов; для schema/prefix migrations нужен отдельный recovery-контракт.
- Собственный init сохраняется, пока его сопровождение разумно. Если service lifecycle мешает надёжности, сравнить с готовым supervisor до расширения собственного.
- Приоритет ближайшей итерации: FIX-01…04 и TEST-02, затем управляемые приложения и повседневные VM-сценарии. Реальная аппаратная графика не блокирует исправление текущей версии; Wayland принят ADR-018.
